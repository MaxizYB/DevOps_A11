# A11 / B11：完整联调全景与材料归属

## 先记住这句话

A11 准备服务器、整合版本和项目输入；B11 在自己电脑提交一次 API 任务；服务器自动跑完整链路；B11 回传独立客户端记录；A11 对照同一个 job_id 汇总交付。中间不需要人来回转发报告。这次做功能/接口联调，不是压力测试。

## 一、一次完整运行，谁在什么时候提供什么

|顺序|责任方|提供/执行|自动还是人工|留下什么|
|---|---|---|---|---|
|0|B11 → A11|B 端源码版本、候选、E11-B 原始结果和测试；本次已收到交接包|人工交接一次|源码 SHA、B11 原始证据、包哈希|
|1|A11|整合 A/B 实现，准备 cJSON 仓库、base/target、Dockerfile、请求，先自测再启动 API|组长部署，脚本检查|部署 SHA/内容指纹、配置 ID、dataset.json、自验结果|
|2|A11 → B11|新版交接 ZIP：客户端、确认后的请求、部署标识、数据清单、回执模板|人工发包一次|双方约定输入；密码另走原私密渠道|
|3|B11|建立 SSH 隧道，运行客户端命令|人工启动一次|操作者声明、起止时间、健康检查|
|4|客户端 → API|POST /v1/jobs，带请求和唯一幂等键；随后查询和下载|自动 HTTP|job_id、trace_id、202 响应、状态轮询、409 检查|
|5|服务器：B11 DRAFT 适配|对 target 的隔离副本构建失败 Dockerfile及修复候选，运行镜像检查输出|自动内部函数调用|两次构建日志、镜像 ID、候选哈希、运行结果|
|6|服务器：A11 BuildChecker|在 base 上 clean + strace 全量构建，记录实际/声明图，交叉核对后建立缓存|自动内部函数调用|full-check.json、baseline-cache.json、图、原始 trace|
|7|服务器：A11 EChecker|消费 base 缓存检查 target；失效时刷新，否则复用；另做 target 全量对照|自动内部函数调用|incremental-check.json、MD/RD、refreshed/reused、对照结果|
|8|服务器：B11 MDFixer 适配|读取本轮 target 增量报告，生成 Makefile 补丁|自动内部函数调用|candidate.patch、repair.json、实际输入报告哈希|
|9|服务器：复验|隔离应用补丁、构建、make test、模拟头文件变新后实际重编译、重新检测|自动内部函数调用|accepted、五项检查、最终无 MISSING 的报告|
|10|客户端|查询成功后下载所有清单文件、核对字节/哈希/提交/配置/部署指纹及阶段衔接|自动 HTTP 与本地校验|verification.json、请求/响应、下载内容、自动结果 ZIP|
|11|B11 → A11|原样回传新 ZIP、填写回执，补缺失个人材料|人工交接一次|B11 独立访问确认|
|12|A11|对照服务器同一个 job_id，整合 A11 报告、B11 联调材料、源码和 CI 追溯，再出最终提交包|组长汇总，脚本核验|最终交付清单、源码 SHA、逐文件 SHA256、未完成项|

表中的 A/B 表示组件实现来源，不表示每个阶段都由该组同学手动操作。当前架构内部组件通过编排器函数和带哈希文件衔接；跨机器 HTTP 是客户端与一个共享任务 API。SSH 只做加密端口转发，请求/响应会自动往返。

## 二、最终交什么，材料从哪里来

|材料|A11 已能自行取得|需要 B11 提供/确认|
|---|---|---|
|最终源码、A11/B11 来源版本、契约、适配代码和测试|A11 仓库与部署目录；保留 B11 来源 SHA|确认 B11 来源版本和职责，不冒充其个人提交|
|A11 E11-A 原始证据与三人报告、ADR、AI/分工记录|A11 原仓库/个人记录/组长云端复核|不需要 B11 代写|
|B11 E11-B 固定 MD 修复证据|收到的 B11 交接包已有原始结果；A11 可另做独立复核|B11 自己的个人报告/ADR/AI 记录及未包含材料；A11 不能代填经历或评审|
|cJSON 来源、完整 base/target SHA、变更说明、构建/测试命令、候选来源|data/ 的 dataset、请求、Dockerfile；实验源码不修改上游历史|双方确认共用输入与分析范围；如实说明开源历史复现选题例外|
|完整五阶段报告、图、trace、缓存、MD、补丁、复验、配置和哈希|服务器自动生成，A11 归档|不需要 B11 再手工转发每个阶段|
|B11 独立 API 访问记录与操作者回执|服务器有服务端同一 job_id 的记录，但不能替代客户端证据|新版客户端自动 ZIP 与填好的回执，必须由 B11 实际操作后回传|
|Issue/分支/PR/CI/Review 与最终源码 SHA|A11 可整理自己的真实记录|B11 如需交个人协作记录，应提供其真实记录；不能编造或冒充批准|

E11-A 的重点是全量图→历史缓存→增量→同目标全量对照；E11-B 的重点是固定 MD→补丁→accepted→无 MD；E12 额外要求本轮真实报告串接、API 访问/幂等/下载证据、真实项目来源。课程生成样例与 cJSON 结果分开归档。

## 三、组长接下来具体要做什么

1. 把新版 cJSON 交接 ZIP 发给 B11，让其用原转发账号运行一次，不要求重新安装 Docker或再写适配。
2. 要回两个东西：自动生成的本轮 cJSON 结果 ZIP、填写的回执。若其个人报告/ADR 尚缺，让他们补齐。
3. 将回传 ZIP 放到本仓库；核对实际部署、job_id、输入和哈希，失败则先排障再新开一轮，不覆盖旧记录。
4. 补齐真实 GitHub 提交/审核/CI 记录，再整理最终 E11/E12 提交包；本轮本地修改不自动等于 GitHub main 已合并。

无需守着五阶段分别点击，也不需要中途把 A11 检测结果发给 B11 再等补丁。若整轮失败，双方根据自动保存的错误和日志定位。

## 四、不要混淆的三种状态

- A11 服务器自验通过：说明整合后的技术链路可用，不代表 B11 已独立访问。
- B11 新版 cJSON API 联调通过：说明本轮实际跨组输入、版本和链路通过，不代表选题符合“本组实际维护”。
- 作业最终可交：还要材料、个人记录和协作追溯齐全。组长同意使用开源历史复现样例，会如实写入选题说明，不写成老师已批准或本组原创维护。
