# ADR：组长 E8–E10 个人验证采用独立预期与动态交叉核对

- 状态：Accepted
- 日期：2026-11-06
- 关联 Issue：#29
- 学号 / GitHub：241880439 / MaxizYB

## 背景与约束

本阶段要求组长本人也完成 A 轨道 E8、E9、E10、每阶段自主测试及个人文档。仓库采用课程提供的受限 C/Make/GCC 教学 profile；参考实现已经由公共环境接入，个人贡献应通过独立测试和可追溯证据体现。服务器可见内存约 3.54 GiB，低于材料建议的 4 GiB，按组长已确认的方案串行运行并如实披露，不降低课程门槛。

## 决策

1. 每个阶段先由 labs/e8e10/leader_cases.py 给出独立固定预期，再分别比较增量报告、全量报告和（可用时）真实 BuildChecker 对象图投影；不把扫描实现自身生成的结果直接当作 Oracle。
2. E8 自主场景在嵌套头文件新增叶节点后检查历史图失效、完整边集合和新增 MD；E9 自主场景把 include 依赖从 main.o 迁移到 helper.o，检查目标身份变化；E10 自主场景切换并恢复条件编译宏，检查两个方向的 added/resolved。
3. E10 标准路线固定六类变化各五次，保留 30 行结果和 60 份成对原始 JSON；自主宏切换另测两个状态各五次。性能统计限定为 scan 墙钟时间，不冒充完整 clean build 或论文级性能。
4. 个人代码只新增学号前缀测试、独立预期和证据 runner；不修改公共扫描算法、workflow、环境镜像或 E7 实现。公共成员成果先合入 main，组长分支以合并后的 7c145d6 为父提交。

## 备选方案与取舍

- 只比较增量和全量结果：无法防止两条路径共同产生同一错误，因此增加独立预期。
- 只比较发现数量：会漏掉目标或依赖边替换，因此比较完整 actual、declared、findings 及 added/resolved。
- 为每次 E10 重复滚动更新缓存：会改变重复测量的实验问题，因此同一场景五次使用同一历史基线。
- 把服务器建议内存改写成实际满足：不符合事实，故保留资源差异并采用串行执行。

## 后果与覆盖范围

方案提高了证据体积和运行时间，但能够追溯输入、样例内部 Git 历史、报告、动态投影和独立 Oracle。结论只覆盖课程限定的两个对象目标、显式本地头文件、Make 配方和 GCC 配置，不推广为任意构建系统或论文完整算法。
