# Issue #31：独立一致性判定与实验身份

日期：2026-11-06；学号：241880411；GitHub：andelutixia；轨道：A / EChecker。

## 背景与约束

[Issue #31](https://github.com/MaxizYB/DevOps_A11/issues/31)要求本人完成 E8、E9、E10，并负责完整集合一致性、五次重复测量及 BuildChecker 动态交叉核对。课程参考入口仅保存每场景末次报告，不能据此复核全部测量，也不能把两份同样错误的报告视为正确。

实验执行时外层源码尚未提交，实际版本由基础提交、源码快照和哈希清单共同标识；样例内部 Git 历史用于描述受测输入。本次按用户确认的范围提交至个人分支，不创建 PR。详细版本信息保留在原始证据中。

## 决策

1. 在扫描前保存手工指定的完整 `actual`、`declared`、`findings` 预期。两条扫描路径既互相比较，也分别与独立预期比较；同数量的错误边或发现仍须失败。允许集合顺序不同，拒绝重复边、重复发现及缺少必需字段。
2. 六个累积场景各测五次。每个场景的五次增量扫描使用同一历史报告的独立副本，保存每次增量/全量 JSON、比较结果和 CSV；重读原始报告检查行数、路径、提交、耗时、复用数量与基线链，不能只相信已保存的 `passed`。
3. 动态 BuildChecker 的实际图、声明图和发现统一投影至 `main.o`、`helper.o`，再作完整集合比较。必须先确认 clean/build 成功及两个目标实际被观测；保留 strace、Make 数据库和报告，不能用 GCC 结果或助教输出替代动态证据。
4. 统计真实 `scan()` 墙钟时间的中位数、最小/最大值和 `full_median / inc_median`。这包含 Git/编译器身份检查、声明解析、必要的 `gcc -MM`，不是 clean build 性能。个人 runner 逐命令写日志的开销包含在其 scan 计时中，扩展场景须披露此差异；比值小于 1 时如实保留。
5. 保留课程 `scan()` 的保守失效策略：本地预处理指令、文件集合、配方或配置变化可刷新两个对象；不宣称实现了论文的完整受影响目标优化。本人的共享间接头、同数量 old→new 替换及真正删除头文件用例验证该边界，不放宽预期掩盖漏边。

## 代价与替代方案

固定 Oracle 只覆盖明确的 C/Make 教学样例，不支持任意工程。保存完整源码、原始报告与日志增加存储和 I/O，但能追溯未提交版本及失败结果。只比较发现数量、只比较两份扫描结果或只保存最后一轮均不满足本任务；按次滚动更新历史基线会改变测量问题，因此不采用。

服务器可见内存约 3.54 GiB，低于材料建议的 4 GiB。组长已接受现有资源串行试跑；记录实际资源，不修改建议门槛，也不把公共环境自检算作个人实验。
