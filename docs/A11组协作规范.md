# A11 组协作规范

本规范适用于 `DevOps_A11` 仓库的日常开发、文档和实验交付。目标是让每项工作都能追溯到负责人、需求、实现、验证结果和评审记录。

仓库当前托管在 GitHub，因此以下以 **Issue** 和 **Pull Request（PR）** 为准；若在 GitLab 镜像仓库协作，**Merge Request（MR）** 与 PR 执行相同规则。

## 1. 基本约定

- 本次初始框架提交是唯一允许直接提交到 `main` 的启动例外；该提交推送后，不直接向 `main` 分支提交，所有会影响交付物的改动通过 PR/MR 合并。
- 后续任务发布、实现、修复、文档变更和实验记录均必须先有 GitHub Issue；没有 Issue 不开始开发分支或合并工作。
- 一个 Issue 只描述一个可验收目标；一个 PR/MR 只解决一个目标或一组紧密相关的目标。
- 提交、Issue、PR/MR 必须能互相追溯：PR/MR 关联 Issue，必要时提交正文也引用 Issue 编号。
- 作者在提交 PR/MR 前完成自查和本地验证；合并前至少获得一名组员评审通过。
- 不提交密钥、令牌、个人配置、构建产物或无关格式化改动。发现敏感信息应立即撤销公开凭据并报告组内。

## 2. Issue 驱动流程

1. 组长或任务提出者按第 5 节模板发布 Issue，写明负责人、交付物和可检查的验收条件。
2. 负责人确认范围和依赖，在 Issue 留言记录计划，并从最新 `main` 创建第 3 节规定的分支。
3. 开发过程中的阻塞、范围变化、关键设计决定和验证结果均更新到原 Issue；不能完成时也必须说明原因和下一步。
4. 负责人创建 PR/MR，通过 `Closes #<issue-number>` 关联 Issue；PR/MR 合并后才关闭已完成的 Issue。
5. 合并者在 Issue 或 PR/MR 留下最终提交 SHA、验证结果和个人贡献摘要，供课程统计与追溯使用。

一个 Issue 必须只有一名明确负责人。协作者可以参与，但不能替代负责人的交付责任。未确定负责人的任务可先发布为待认领，未认领前不得进入开发。

## 3. 分支命名

从最新 `main` 创建工作分支，格式如下：

```text
<type>/<issue-number>-<short-description>
```

`type` 只能使用 `feat`、`fix`、`docs`、`test`、`refactor`、`build`、`ci` 或 `chore`。`short-description` 使用简短英文小写短语，以连字符分隔。

```text
feat/12-draft-job-api
fix/23-baseline-validation
docs/31-collaboration-guide
```

分支编号必须对应 Issue 编号。初始框架推送后，即使是文档、调研或维护工作也必须先创建 Issue；不再使用无编号的临时开发分支。

## 4. Commit 格式

### 4.1 标题

采用 Conventional Commits 格式：

```text
<type>(<scope>): <简明说明>
```

- `type`：`feat`（新功能）、`fix`（缺陷修复）、`docs`（文档）、`test`（测试）、`refactor`（重构）、`build`（构建）、`ci`（持续集成）、`chore`（维护）。
- `scope`：可选，填写受影响模块，例如 `draft`、`checker`、`api`、`contracts`、`docs`。
- 说明使用动词开头，表达实际变化，不写 `update`、`fix bug`、`修改一下` 等笼统描述；建议不超过 72 个字符。

示例：

```text
feat(draft): add Dockerfile job endpoint
fix(checker): reject a baseline with a mismatched commit
docs(contracts): define artifact URI consumption rules
test(repair): cover a missing dependency report
```

### 4.2 正文与关联

当标题不足以说明原因、影响或验证方式时，空一行后补充正文。需要关联任务时使用完整引用：

```text
fix(checker): reject a baseline with a mismatched commit

Validate the baseline commit before starting incremental analysis.

Refs #23
```

- 除初始框架提交外，提交正文必须以 `Refs #<issue-number>` 关联所属任务；一个提交只做一类清晰变更，避免把功能、重构和无关格式化混在一起。
- 提交前运行与改动相符的检查；无法运行时，在 PR/MR 中说明原因。
- 修复型提交保留能重现问题的测试或最小复现材料。

## 5. Issue 规范

### 5.1 标题

格式：

```text
[<stage>][<area>] <可验收的交付目标>
```

- `stage`：课程阶段，例如 `E2`、`E3`。
- `area`：工作边界，例如 `contract`、`baseline`、`buildchecker`、`echecker`、`integration`、`docs`、`test`。

示例：

```text
[E2][contract] 建立 A/B 共享任务与产物契约
[E2][buildchecker] 准备全量 MD/RD 检测交付物
[E2][echecker] 准备跨提交增量检测交付物
[E3][baseline] 建立测试基线规范并汇总交付证据
```

### 5.2 发布要求与正文模板

发布者必须在创建 Issue 前写清负责人、预期分支、交付物、验收条件、依赖与非范围。E2 使用 `.github/ISSUE_TEMPLATE/e2-task.md`，E3 使用 `.github/ISSUE_TEMPLATE/e3-task.md`；任务正文至少包含以下内容：

```markdown
## 任务信息
- 阶段：E2
- 模块：
- 负责人：@
- 预期分支：`<type>/<issue-number>-<short-description>`
- 依赖 Issue：无；或 #

## 背景与目标
<!-- 为什么需要这项工作；完成后能交付什么。 -->

## 交付物
- [ ]

## 验收条件
- [ ]
- [ ]

## 非范围
<!-- 明确本 Issue 不实现、不修改或不负责的内容。 -->

## 验证与证据
- 命令或检查方法：
- 预期结果：
- 证据保存位置：

## 风险与阻塞
- 风险：
- 阻塞时的更新方式：在本 Issue 留言说明原因、已尝试内容和下一步。
```

- 验收条件必须可检查，例如“无 `baseline` 字段时 API 返回 400 和明确错误码”，而不是“功能正常”。
- E3 基线任务还必须写清 fixture/work/evidence 路径、固定源码版本或生成方法、环境/配置、可重放命令、预期 Oracle 和实际观察的保存方式。
- Issue 创建时标注课程阶段、模块和状态；本仓库使用 `stage:E2`、`stage:E3`、`area:baseline`、`area:contract`、`area:buildchecker`、`area:echecker`、`status:ready` 等标签。
- 阻塞、范围变化或无法完成时，在原 Issue 留下说明，不静默搁置。

## 6. PR/MR 规范

### 6.1 标题与关联

- 标题沿用 Commit 格式，例如 `feat(draft): add Dockerfile job endpoint`。
- 目标分支为 `main`，源分支遵守第 3 节命名。
- PR/MR 正文使用 `Closes #<issue-number>` 关联并在合并后自动关闭已完整解决的 Issue；未完整解决时使用 `Refs #<issue-number>`。

### 6.2 正文模板

```markdown
## 关联任务
Closes #<issue-number>

## 改动说明
- <改动项>

## 验收与验证
- [ ] 已完成 Issue 中的验收条件
- [ ] 已运行：`<命令>`
- [ ] 结果：

## 影响与兼容性
- API / Schema / 配置 / 数据迁移：无；或说明变更和兼容策略

## 证据
- 日志、截图、报告或产物链接：

## 课程追溯
- 作者：@
- 个人贡献：
- AI 使用记录：无；或链接至 `AI_USAGE.md` 的对应记录
```

涉及接口契约、Schema、构建配置或依赖报告时，PR/MR 必须额外说明：输入输出变化、版本兼容性、失败行为和下游验证方式。

### 6.3 合并条件

满足以下条件才可合并：

- PR/MR 描述完整，关联的 Issue 和验收条件明确。
- 作者已自查，至少一名非作者组员批准评审。
- 必需的测试、校验或人工验证通过；失败或未执行的检查有明确说明并被评审者接受。
- 不包含冲突、调试残留、敏感信息或与任务无关的文件。
- 文档、接口和测试随实现同步更新。

默认采用 **Squash and merge**，以 PR/MR 标题作为合并提交标题，保持 `main` 历史清晰。确实需要保留多个独立提交的技术演进时，经评审者同意后可使用普通合并。

## 7. 评审与反馈

- 评审关注正确性、验收条件、测试证据、接口兼容性、可维护性和是否超出 Issue 范围。
- 评论应指出具体文件、行为和期望结果；作者应回复每条评审意见，说明已修改或不采纳的理由。
- 对请求修改的 PR/MR，作者修订后重新请求评审；不要自行关闭未解决的评审讨论。
- 紧急修复也要保留 Issue 和 PR/MR 记录；可先获得一名组员确认后合并，再补齐完整验证证据。

## 8. 最小交付链示例

```text
Issue #23 [E2][echecker] 拒绝不匹配的增量检测基线
  -> 分支 fix/23-baseline-validation
  -> Commit fix(echecker): reject a baseline with a mismatched commit
  -> PR fix(echecker): reject a baseline with a mismatched commit
  -> PR 正文包含 Closes #23、测试命令和结果
  -> 评审通过后 squash merge 到 main
```

本规范从首次合并起执行。变更本规范本身时，使用 `docs(collaboration): ...` 提交，并通过 Issue 和 PR/MR 讨论后合并。
