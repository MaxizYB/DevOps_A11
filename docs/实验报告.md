## E5：原始复现

入口：`python3 scripts/lab_cloud.py e5 --image <本次image-id> --out work/<新目录>`。

在容器内复制固定输入 `fixtures/md-rd/`，执行 `make clean`，再用 `strace -ff -s 4096 -e trace=%file,%process make -p app` 采集每个进程的原始系统调用和 Make 数据库。最后运行 `./app`，预期/实际输出均为 `1`，E5 入口退出 0。

| 目标 | 实际读依赖 | Make 声明 | 结论 |
| --- | --- | --- | --- |
| main.o | main.c、config.h | main.c、unused.h | MD(config.h)、RD(unused.h) |
| app | main.o | main.o | 一致 |

组长 10 月 20 日真实锚点为 `evidence/leader/e5-01/evidence/trace/t.16:580`（成功打开 config.h）及 `make-db.txt:1049`（声明 main.o）。最终重放锚点由交付包 `核验结果.json` 重新列出，不假定 PID 和行号跨运行相同。

`cc` 派生 `cc1` 和 `as`，前者读取头文件、后者写出 main.o；沿成功 fork/clone 和 exec 的父子链归入同一 recipe，不能把读取和写出割裂成不同目标。仅统计项目内成功读打开，失败打开、系统头文件和临时文件被过滤。

论文使用 ptrace 并评估多个开源项目；本组采用 strace 和已知 MD/RD 的教学 fixture，只复现核心流程，不声称完成论文 benchmark 或重现论文性能指标。

## E6：核心能力及证据

CLI：`python3 -m buildchecker full-check --fixture <输入> --out <新证据目录> --fail-on-findings`。ECS 包装入口为 `lab_cloud.py e6`。

1. 复制输入、保存 SHA256，执行 clean build。
2. 重建进程树，按 fork 时 cwd 解析项目内读写；同 recipe 子进程合并归属。
3. 从 `make -p` 的 Files 段建立声明图；展开 PHONY，order-only 单独保存。
4. 对相同目标求 `Actual - Declared` 得 MD，`Declared - Actual` 得 RD，输出 findings、两图、进程及原始证据。

原始样例必须 `status=SUCCEEDED`、clean/build 均 0，findings 精确为 `MISSING(main.o, config.h)`、`REDUNDANT(main.o, unused.h)`；因启用发现门禁，CLI 退出 1，是预期行为而非检测失败。

`--fixed` 只改独立副本：`main.o: main.c unused.h` → `main.o: main.c config.h`。修复后 findings 为空、CLI 退出 0，输入文件集合相同，只有 Makefile 哈希变化。校验命令：

```sh
python3 scripts/verify_e6_evidence.py \
  --before work/<before>/evidence/findings.json \
  --after work/<after>/evidence/findings.json
```

成员完整记录见 [evidence/e6/issue-21-validation.md](evidence/e6/issue-21-validation.md)。其原始 trace `t.14:579` 读取 config.h，`t.15:23` 写出 main.o，`make-db.txt:1041` 声明 unused.h；PID 14/15 同属 cc 作业 13。成员 before/after trace_id 分别为 `e6-ecf93a06cc984cbf8e0fc02e9680e1d8`、`e6-8558ed7d4cdf4fb8a6a72e79b28ccd85`。

本次四项新增回归测试验证成功/失败的 Make chdir 和 symlink/symlinkat：不支持的成功操作明确返回 `FAILED/UNSUPPORTED`，失败调用不制造假依赖。证据包保留真实 Linux 边界复现及输入审计。
